# Shopify webhook inbox privacy and retention

Delivery API remains the only durable Shopify webhook inbox. Order admission stores only a `shopify_order_reference_v1` replay envelope containing the canonical order GID; customer email, phone, name, note, shipping address, and other parsed order fields never enter the inbox in `QUEUED`, `PROCESSING`, `RETRY_WAIT`, `FAILED`, or `DEAD_LETTER` state. A successful terminal transition atomically replaces that envelope with `shopify_webhook_tombstone_v1`; the `(shopId, webhookId)` row remains so duplicates are accepted without another business effect. `rawBodySha256` is the only raw-body derivative retained.

`customers/redact` takes a transaction-scoped advisory lock for each app/shop/legacy order identity, creates a permanent non-PII `ShopifyOrderRedactionTombstone`, removes the canonical order, minimizes historical inbox rows, and records the sanitized compliance receipt in one serializable transaction. Every Shopify canonical upsert takes the same lock and returns `ORDER_PRIVACY_REDACTED`/`skipped` before any order or stop write when a tombstone exists. This prevents an already-claimed worker, a later retry, or a reconciliation refetch from recreating deleted customer data; distinct future legacy order IDs remain unaffected. `shop/redact` deletes the `Shop` and shop-scoped data, but preserves the independent app/domain tombstone and minimal webhook receipt outside that cascade. Those non-PII records suppress response-loss retries and delayed prior-install webhooks. A verified reinstall advances the lifecycle epoch without erasing prior receipts.

The webhook route accepts signed JSON bodies up to 5 MiB by default, independently of unrelated API routes. `SHOPIFY_WEBHOOK_BODY_LIMIT_BYTES` may be set from 1 MiB through 10 MiB; invalid or out-of-range configuration fails startup. Bodies above the configured limit receive `413` before inbox admission.

The scheduled `shopify:webhook-events:cleanup` command deletes only `PROCESSED` and `IGNORED` rows older than `SHOPIFY_WEBHOOK_TERMINAL_RETENTION_DAYS`. The default and minimum are 30 days, preserving a bounded duplicate-detection window. `RECEIVED`, `QUEUED`, `PROCESSING`, `RETRY_WAIT`, `FAILED`, and `DEAD_LETTER` rows are never retention candidates because they may require retry or operator reconciliation.

Order redaction tombstones are legal suppression evidence, not webhook delivery receipts. They contain no customer payload and are not deleted by terminal webhook retention.

The repository-owned hourly systemd wrapper runs this cleanup alongside driver-event and proof-media cleanup. Each command drains bounded batches until empty or its row/time budget is reached. A remaining backlog exits non-success so systemd and logs expose immediate-continuation/alert evidence instead of reporting a partial run as healthy.
