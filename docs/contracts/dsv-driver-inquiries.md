# DSV Driver inquiries

## Scope

Drivers can create and read their own plain-text support inquiries. Development
administrators can read inquiries from accounts currently linked to their shop.
There are no reply, status, attachment, update, or delete endpoints in this version.
Do not treat a body as HTML. Never ask drivers to include passwords or tokens.

## Driver API

Base: `https://clever-route-api.cleversystem.ai`.
Use the DSV login/refresh **account access token**, not a route token, in
`Authorization: Bearer <accessToken>`. Each operation checks the current active
account and token version. Responses are `Cache-Control: private, no-store`.

| Operation | Request | Success |
| --- | --- | --- |
| Create | `POST /api/dsv/driver/inquiries` | 201; replay 200 |
| List | `GET /api/dsv/driver/inquiries?limit=20&cursor=<opaque>` | 200 |
| Detail | `GET /api/dsv/driver/inquiries/:id` | 200 |

Create requires JSON `{ "title": "…", "body": "…" }` and a UUID
`Idempotency-Key`. Unknown fields are rejected. After trimming, title length is
1–120 and body length is 1–4000 (JavaScript UTF-16 code units); NUL is rejected.
The transport limit is 24,000 bytes, with the existing rate limiter capped at
10 create requests per minute. Author/account/time must not be supplied by clients.

An inquiry is `{ id, title, body, authorName, createdAt }`; `createdAt` is a
server-generated ISO UTC timestamp. Create returns
`{ data: { inquiry, duplicate: false }, error: null }`. Keep the same UUID when
retrying the same submission. Same account, key, and trimmed content returns the
original inquiry with `duplicate: true`; changed content returns 409
`IDEMPOTENCY_CONFLICT`. A new draft needs a new key.

List returns `{ data: { items: [inquiry], nextCursor: string | null }, error: null }`.
Limit defaults to 20 and accepts integers 1–50. Ordering is `createdAt DESC, id DESC`;
timestamps are stored at millisecond precision to preserve the Date cursor boundary.
Pass the returned cursor unchanged; it does not confer permission to read another
account. Detail returns `{ data: { inquiry }, error: null }`. Foreign and missing
IDs both return 404 `NOT_FOUND`. Additional query keys are rejected.

Errors use `{ data: null, error: { code, message } }`. Branch on status/code, not
message wording: 400 `BAD_REQUEST` (malformed JSON: `INVALID_JSON`), 401
`UNAUTHORIZED`, 404 `NOT_FOUND`, 409 `IDEMPOTENCY_CONFLICT`, 413
`PAYLOAD_TOO_LARGE`, 429 `RATE_LIMITED`, and sanitized 500 `INTERNAL_SERVER_ERROR`.
Every response from these five driver/admin inquiry routes, including parser,
size-limit, rate-limit, authentication, and unexpected-error responses, is
`Cache-Control: private, no-store`. Cursor timestamps accept only the same
four-digit-year, millisecond UTC form generated by the server (years 0001–9999).
Unexpected repository failures are logged as a static inquiry event with request
metadata only. A Prisma-shaped `P` plus four-digit code may be retained for
diagnosis; inquiry content, raw error text, custom names, and metadata are not logged.

## Development administrator reads

`GET /api/dsv/driver-inquiries` and `GET /api/dsv/driver-inquiries/:id` use the
existing admin cookie session with `dsv:accounts:read`, re-resolved on each request.
They share the list/detail envelopes and pagination rules. Driver bearer tokens
alone are not admin authentication. Ordinary operator scopes are insufficient.
No new account, scope grant, or privilege escalation is part of this feature.

The filter is the authenticated session's `shopId` through the **current**
account → driver → shop relationship. Client shop overrides are rejected. A
foreign-shop ID is indistinguishable from a nonexistent ID. Unlinked accounts'
inquiries remain owner-only; this is not a global support inbox. Do not weaken
that boundary to make unlinked inquiries visible.

## Retention and concurrency

Inquiries are retained while an account is maintained. Account deletion fulfillment
removes all inquiry content and stored author names in the same transaction as
the existing account anonymization. A foreign key cascade also covers physical
account deletion. Create and fulfillment lock the same account row before writing
or removing inquiries, so a simultaneous submission cannot survive completed deletion.
Unrelated accounts' inquiries are untouched. Public Driver privacy describes these
fields, access boundaries, purpose, and retention; keep it aligned with implementation.

## Release and recovery

Apply the additive `20260907010000_dsv_driver_inquiries` migration before serving
this API. Run G007 empty and backup → guarded restore → upgrade rehearsals with
zero final drift, the disposable inquiry integration tests, route/auth tests,
account-deletion tests, and privacy tests. Existing schema drift is a separate
hotfix; it must not be hidden or marked as a successful rehearsal.

Deploy through the existing Route Ops GitHub Actions lane after exact-SHA CI.
Verify health/ready, actual runtime revision, both real API account-isolation
directions using only synthetic accounts, idempotent replay, and public policy.
Do not modify actual routes or store-review passwords during QA.

The migration is additive and old images ignore the new table, but **image rollback
is not full behavioral rollback**: old account-deletion code does not remove these
rows. Before real adoption, keep the app feature unshipped until runtime QA passes.
After inquiries exist, prefer a forward fix retaining deletion cleanup. Emergency
rollback must also stop new inquiry creation and pause deletion fulfillment until
the inquiry-aware handler is restored; never drop the table or discard user content
as routine rollback. Database restore is an incident recovery action, not an
automatic downgrade. Keep an approved pre-migration backup and the guarded restore
evidence; do not restore over live production during a rehearsal.
